## Synthèse des écarts et réserves

### Écart à traiter (point 2 — dosage)

**Durée max 600 s non appliquée côté serveur.** Le garde-fou existe dans le moteur (`SessionRunner.prochain_item`, `runner.py:101-103`) mais le backend consomme tous les items à l'ouverture de la séance (`service.py:167`) : aucun contrôle du temps écoulé n'existe dans `repondre()` ni `terminer()`. Démonstration (exécution en mémoire, dépôt intact) :

```
1) réponse soumise après 1200 s : acceptée (correcte = False)
2) réponse suivante après dépassement : acceptée (correcte = True)
3) fin() clôture normalement : duree_s = 1200 · arret_propose = False
```

Conséquence clinique : une séance peut s'étirer indéfiniment (pauses longues entre items) sans aucun signal serveur, sortant du cadre de dosage 5-10 min des protocoles. La détection de fatigue reste opérationnelle (RT/erreurs par item), mais la borne temporelle n'est qu'informative (`regles.duree_max_s` dans le payload).

**Périmètre du quota journalier.** « 3 séances/jour » est implémenté **par thème** (`service.py:144-147`), soit jusqu'à 9 séances/jour sur 3 thèmes. Le contrat (`api-contract.md`) et les protocoles énoncent « 3 séances/jour » sans préciser le périmètre. À trancher explicitement (cap global recommandé, ou justification clinique du choix par thème).

### Réserves mineures (sans risque clinique direct)

1. **Point 3** — métadonnées FastAPI visibles sur `/docs`/`/openapi.json` : titre « Bilan & rééducation cognitive (SPC) » et description mentionnant bilan/rééducation (page développeur, hors UI d'entraînement). Titre neutre ou désactivation de `/docs` recommandée en usage familial.
2. **Point 3** — READMEs de développement sous `frontend/src/` servis statiquement via `/ui/src/...` (mentionnent bilan/rééducation hors contexte UI). À exclure du montage statique.
3. **Point 5/6** — errorless d'entrée de palier pas encore en contenu (types `production`/`prediction-sortie` seuls livrés) ; prerequis vides sur python/anglais (chaînage complet uniquement sur calcul-mental).

### Ce qui est remarquable (à conserver)

- Le verrou anti-régression est réel : des tests dédiés verrouillent chaque garde-fou clinique (fatigue jamais forcée ×3 niveaux : moteur, service, API ; payload sans réponse vérifié récursivement sur les 3 thèmes ; absence d'endpoint bilan ; 429 corps exact).
- La séparation vocabulaire est effective : aucune chaîne utilisateur construite hors `messages.py` (router = codes machine + prose centralisée).
- Le contenu est entièrement machine-validable (`tools/validate_items.py`) et la traçabilité de relecture (`a_revoir` partout) est honnête — aucune sur-promesse.
